# Loops Trd

Закрита P2P-площадка для обміну **USDT ⇄ UAH** між друзями. Вхід лише за запрошенням, кошти продавця тримає ескроу-смарт-контракт, кожну угоду перевіряє антифрод.

> ⚠️ Лише **BNB Smart Chain Testnet** і тестовий токен **mUSDT**. Mainnet свідомо не налаштовано: деплой-скрипт і сервер відмовляються працювати з chainId 56/1.

## Як це працює

```
Покупець відгукується на оголошення
   │  сервер: ролі → антифрод (3 шари) → угода в БД (атомарно, ліміти не обійти паралельними запитами)
   ▼
Продавець отримує EIP-712 підпис сервера і вносить USDT в ескроу (createDeal → approve → deposit)
   │  30 хв на оплату (час паузи контракту не рахується)
   ▼
Покупець платить гривнею зі своєї картки, вказує ім'я відправника, тисне «Я оплатив» (markPaid)
   ▼
Продавець бачить гроші в БАНКУ (не скріншот), підтверджує ім'я відправника
   │  сервер: антифрод → approveRelease (середній ризик — підпис гаманцем; інше ім'я — перевірка модератором;
   │          високий — freezeDeal до рішення адміна)
   ▼
confirmRelease → контракт відправляє USDT покупцю
```

- **Немає оплати 30 хв** → ще 15 хв **пільгового періоду** (покупець, що вже заплатив, відкриває спір) → кіпер повертає USDT продавцю. Якщо покупець вказав оплату, але не натиснув кнопку — кіпер **заморожує**, а не скасовує.
- **Спір**: модератор рекомендує, адмін виконує `resolveDispute` зі свого гаманця; сервер звіряє розподіл із подією в блокчейні.
- **Чат** у кожній угоді; після закриття повні номери карток маскуються.
- **Журнали**: усі дії в угодах (час, гаманець, дія, tx), окремо — дії адмінів/модераторів (з підписами) і системні події.

**Стек:** Next.js 16 (App Router) · React 19 · Tailwind 4 · Reown AppKit + wagmi 2 + viem · Supabase Postgres + RLS · Solidity 0.8.28 + Hardhat + OpenZeppelin 5.

## Швидкий старт

Потрібні Node.js 20+ (перевірено на 22) і Trust Wallet або MetaMask.

```bash
cd loops-trd/contracts && npm install
cd ../web && npm install && cp .env.example .env.local
```

### 1. Reown Project ID

1. **https://dashboard.reown.com** → Create Project → AppKit → Next.js.
2. Project ID → `NEXT_PUBLIC_REOWN_PROJECT_ID`.
3. У налаштуваннях проєкту (**Domain / Allowlist**) додайте `localhost:3000` і продакшн-домен.

### 2. Supabase

1. Створіть проєкт на **https://supabase.com** (регіон — Frankfurt).
2. Міграції — по черзі файли з `web/supabase/migrations/` у **SQL Editor** або:
   ```bash
   cd loops-trd/web && npx supabase login && npx supabase link --project-ref <ref> && npx supabase db push
   ```
3. **Project Settings → Database → Connection string → Session pooler** (порт 5432) → `DATABASE_URL`.
4. **Database → SSL Configuration → Download certificate** → вміст у `DATABASE_CA_CERT` (перевірка сервера БД).
5. `SESSION_SECRET` — **окремий** випадковий рядок: `openssl rand -base64 48`.
   Не використовуйте JWT secret Supabase: тоді сесійний токен дав би прямий доступ до Supabase API (RLS усе одно діє, але це зайва поверхня атаки).

**Авторизація.** Вхід — SIWE (підпис гаманцем). Сервер перевіряє підпис, домен, адресу сайту, мережу та одноразовий nonce і видає httpOnly-cookie з JWT (з ідентифікатором сесії — вихід відкликає токен на сервері). Кожен запит від імені користувача виконується з `SET LOCAL ROLE authenticated` + `request.jwt.claims`, тож **RLS-політики діють і для серверного коду**.

### 3. Тестові BNB з фаусета

tBNB потрібні деплоєру, **серверному гаманцю** (`BACKEND_SIGNER_PRIVATE_KEY`: approveRelease, freezeDeal, cancel), учасникам і адміну.

1. Мережа в гаманці: BNB Smart Chain Testnet, chainId **97**, RPC `https://data-seed-prebsc-1-s1.bnbchain.org:8545`, символ **tBNB** (AppKit додасть сам).
2. Фаусет: **https://www.bnbchain.org/en/testnet-faucet** (може вимагати трохи BNB у mainnet або вхід через GitHub; альтернативи — фаусети QuickNode, Chainstack).
3. mUSDT учасник бере в кабінеті кнопкою «Отримати 1000 mUSDT» (раз на годину).

Дашборд адміна показує баланс газу серверного гаманця й попереджає, коли він закінчується.

> Окремі тестові гаманці для деплоєра й сервера. Ніколи не використовуйте ключі з реальними коштами.

### 4. Деплой контракту

```bash
cd loops-trd/contracts && cp .env.example .env
#   DEPLOYER_PRIVATE_KEY, ADMIN_ADDRESS (DEFAULT_ADMIN + ARBITER), BACKEND_SIGNER_ADDRESS (SIGNER + FREEZER)
npm test                    # 76 тестів, вкл. fuzz/інваріанти; покриття 100%
npm run deploy:testnet      # MockUSDT + LoopsTrdEscrow → deployments/bscTestnet.json
```

Адреси → `ESCROW_ADDRESS`, `USDT_ADDRESS` у `web/.env.local`. Після зміни контракту: `npm run export-abi`.
Якщо компілятор не завантажується (фаєрвол) — `USE_SOLCJS=true`.
Рекомендовано: `ADMIN_ADDRESS` — мультипідпис **Safe** (https://app.safe.global, підтримує BSC Testnet), щоб втрата одного ключа не заблокувала спори.

### 5. Запуск

```bash
cd loops-trd/web
npm run dev                  # http://localhost:3000
npm run build && npm start   # продакшн (збірка через webpack)
```

`APP_DOMAIN` має **точно** збігатися з адресою в браузері. Перший адмін: впишіть гаманець у `BOOTSTRAP_ADMIN_WALLET` (той самий, що `ADMIN_ADDRESS` у контракті) і увійдіть — профіль адміна створиться, поки в системі немає жодного адміна. Далі: Адмінка → Учасники → Інвайт-коди.

**Vercel:** Root Directory `loops-trd/web`, Build Command `npm run build`, усі змінні з `.env.example`.

## Кіпер: автоскасування та звірка з блокчейном

`/api/cron/keeper` (заголовок `Authorization: Bearer $CRON_SECRET`):

- скасовує угоди без депозиту понад 30 хв;
- **індексує події контракту** з останнього обробленого блоку (курсор у БД) — депозит/оплата підхоплюються, навіть якщо вкладку закрили;
- **звіряє всі активні угоди** з контрактом і виявляє розбіжності для нещодавно закритих (тривога адміну);
- після дедлайну + пільгового періоду скасовує (USDT → продавцю) або заморожує, якщо покупець указав оплату;
- стежить за газом серверного гаманця, прибирає прострочені службові записи, надсилає сповіщення в Telegram.

Кіпер має працювати **без відкритого сайту** — оберіть один (краще два) способи:

| Спосіб | Частота | Налаштування |
|---|---|---|
| **Supabase pg_cron** (рекомендовано) | щохвилини | виконайте `web/supabase/cron.sql` у SQL Editor (секрет — у Vault) |
| **GitHub Actions** (резерв) | кожні 5 хв | `.github/workflows/loops-trd-keeper.yml`: secrets `LOOPS_KEEPER_URL`, `LOOPS_CRON_SECRET`, variable `LOOPS_KEEPER_ENABLED=true` |
| **Воркер** на VPS/Docker | кожні 30 с | `npm run worker` (ті самі змінні середовища) |
| Vercel Cron | раз на добу (Hobby) | `vercel.json` — лише страховка |

Дашборд адміна показує, коли кіпер працював востаннє (червоне — понад 10 хв).

## Telegram, Sentry, IP за проксі

**Telegram-бот сповіщень** (нові угоди, депозит, оплата, спори, рішення):
1. @BotFather → `/newbot` → токен у `TELEGRAM_BOT_TOKEN`, ім'я бота (без @) у `TELEGRAM_BOT_USERNAME`.
2. `TELEGRAM_WEBHOOK_SECRET` — довільний рядок (`openssl rand -hex 24`).
3. Підключіть webhook:
   ```bash
   curl "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
     -d "url=https://ВАШ_ДОМЕН/api/telegram/webhook" -d "secret_token=$TELEGRAM_WEBHOOK_SECRET" -d 'allowed_updates=["message"]'
   ```
4. Учасник: Кабінет → «Підключити Telegram» → Start у боті. Повідомлення йдуть через outbox (без дублів, з повторами).

**Sentry:** `SENTRY_DSN` (сервер) і `NEXT_PUBLIC_SENTRY_DSN` (браузер). Без них помилки пишуться в логи хостингу; системні події (помилки кіпера, розбіжності, газ) — також в Адмінка → Журнал → «Система».

**IP клієнта** (антифрод, ліміти частоти): на Vercel — `TRUSTED_IP_HEADER=x-real-ip`; за Cloudflare — `cf-connecting-ip`; за nginx — `TRUST_PROXY_HOPS=1` (кількість довірених проксі). Перший запис `X-Forwarded-For` не використовується — його підставляє клієнт.

## Ролі та права

Права перевіряються **на чотирьох рівнях**: інтерфейс → сервер → RLS у Postgres → смарт-контракт.

| Дія | Учасник | Модератор | Адмін |
|---|:-:|:-:|:-:|
| Свої оголошення та угоди, чат | ✓ | — | — |
| Чужі угоди, чат, сигнали ризику | — | ✓ | ✓ |
| Рекомендація у спорі; підтвердження перевірки (кошти все одно відпускає продавець) | — | ✓ | ✓ |
| Відпустити кошти покупцю | лише продавець своєї угоди | **ніколи** | **ніколи** |
| `resolveDispute`, `unfreezeDeal`, пауза контракту | — | — | ✓ (гаманець з роллю) |
| Учасники, ролі, ліміти, чорний список, налаштування антифроду | — | перегляд | ✓ + підпис гаманцем |
| Журнал персоналу / системний журнал | свої дії / — | свої дії / — | усі / ✓ |

## Антифрод

`web/src/server/antifraud/`: `engine.ts` — чиста функція, `repository.ts` збирає факти, `providers.ts` — інтерфейси AML/IP-розвідки.

- **Шар 1 (блок до депозиту / заморозка після):** чорні списки гаманця, картки (4 цифри), пристрою, IP; разовий і добовий ліміти; AML-ризик гаманця (заглушка + каркас AMLBot).
- **Шар 2 (сигнали з вагою й поясненням):** пристрій (FingerprintJS), спільні IP/пристрої/картки/гаманці, VPN/проксі, часовий пояс, швидкість (1 год / 24 год проти історії), різкий ріст суми, нетиповий час, надто швидка оплата/підтвердження, вік акаунта, історія спорів, невідповідність імені відправника, пов'язані сторони угоди.
- **Шар 3:** комбінації (напр. новий акаунт + новий пристрій + велика сума → високий ризик).
- **Рішення:** низький — автоматично; середній — підпис продавця гаманцем (або модератор); **невідповідність імені — завжди модератор**; високий — заморозка в контракті.
- **Ліміти** зростають з кількістю успішних угод; персональні — від адміна.
- **Зворотний зв'язок:** розмітка спорів «шахрайство / чесна» → точність і повнота кожного сигналу; ваги, пороги, комбінації, ліміти редагуються в адмінці (з підписом гаманця).
- Учасники **не бачать** сигналів і пояснень (закрито і в API, і правами на колонки в БД).

## Тести та CI

```bash
cd loops-trd/contracts
npm test                         # 76: юніт + fuzz/інваріанти (fast-check, FUZZ_RUNS=300 для глибшого)
npm run coverage                 # 100% рядків/гілок/функцій для LoopsTrdEscrow і MockUSDT
slither . --hardhat-ignore-compile --filter-paths "node_modules|contracts/test" --exclude-dependencies

cd ../web
npm run lint && npm run typecheck
npm test                         # 113: RLS, антифрод, сценарії угод, права, ліміти частоти, сесії, Telegram, UX
npm run build && npm run e2e     # API-сценарій: локальний вузол (chainId 97) + Postgres + next start (50 перевірок)
npm run e2e:ui                   # Playwright: вхід з інвайтом, оголошення, повна угода, скасування, спір
```

**Fuzz-інваріанти контракту:** баланс ескроу = сума активних угод; токени не зникають і не з'являються; кінцеві стани незмінні; відпуск лише після схвалення; з будь-якого стану адмін може вивести всі кошти (жодних застряглих USDT); сторонні акаунти не можуть забрати чужі кошти.

**GitHub Actions** (`.github/workflows/`): `loops-trd-ci.yml` — на кожен push: контракти (тести, покриття, Slither з `--fail-medium`), сайт (лінтер, типи, тести, збірка), e2e (API + Playwright). Також `loops-trd-keeper.yml` (резервний кіпер) і `loops-trd-backup.yml` (щоденний зашифрований бекап, див. [docs/BACKUP.md](docs/BACKUP.md)).

## Безпека та обмеження

**Зроблено:** RLS на всіх таблицях; підписи гаманця для критичних дій адміна; одноразові nonce (SIWE, дії); перевірка домену, адреси сайту й мережі в SIWE; відкликання сесій; обмеження частоти запитів (у Postgres — працює на serverless); перевірка Origin (CSRF) + SameSite cookie; CSP, HSTS, X-Frame-Options; валідація всіх вхідних даних (zod) і обмеження в БД; секрети лише на сервері; TLS до БД з перевіркою сертифіката; черга транзакцій серверного гаманця; React екранує вивід (XSS), Telegram — без HTML-розмітки.

**Обмеження / що врахувати:**
- Відбиток браузера та часовий пояс надсилає клієнт — це сигнали, не докази.
- VPN/проксі — евристика за заголовками; для точності підключіть сервіс IP-розвідки (`IpIntelProvider`).
- AML — заглушка; для AMLBot реалізуйте запит у `AmlBotProvider` за їхньою документацією.
- Вхід підтримує звичайні гаманці (EOA: Trust Wallet, MetaMask); смарт-гаманці (ERC-1271) — ні.
- `npm audit`: високих уразливостей немає; помірні (decode-uri-component, uuid) — у залежностях конекторів MetaMask/WalletConnect, виконуються в браузері гаманцем і не впливають на сервер; оновлення — коли їх оновить Reown/MetaMask.
- Серверний ключ може лише підписувати створення угод, заморожувати й дозволяти відпуск — перевести кошти собі він не може. Ключ адміна вирішує спори — тримайте його на апаратному гаманці або в Safe.

## Чекліст перед тим, як давати доступ друзям

1. Контракт задеплоєно в BSC Testnet; `ADMIN_ADDRESS` — ваш апаратний гаманець або Safe; на серверному гаманці ≥ 0.1 tBNB.
2. Усі змінні з `.env.example` задано; `SESSION_SECRET` — окремий; `DATABASE_CA_CERT` задано; `TRUSTED_IP_HEADER`/`TRUST_PROXY_HOPS` — під ваш хостинг.
3. Кіпер працює: дашборд адміна показує «щойно» / до 2 хв (pg_cron + резервний GitHub Actions).
4. Пройдіть угоду самі з двох гаманців (купівля, скасування, спір із рішенням), перевірте сповіщення в Telegram.
5. Увімкніть бекапи (Supabase PITR та/або `loops-trd-backup.yml`) і один раз відновіть копію за [docs/BACKUP.md](docs/BACKUP.md).
6. Reown: домен в allowlist; Sentry — DSN (за бажанням).
7. Надішліть друзям посилання на `/help` разом з інвайт-кодами.
