# Loops Trd

Закрита P2P-площадка для обміну **USDT ⇄ UAH** між друзями. Вхід лише за запрошенням, кошти продавця тримає ескроу-смарт-контракт, а антифрод перевіряє кожну угоду.

> ⚠️ Лише **BNB Smart Chain Testnet** і тестовий токен **mUSDT**. Mainnet свідомо не налаштовано: деплой-скрипт і сервер відмовляються працювати з chainId 56/1.

## Як це працює

```
Покупець відгукується на оголошення
   │  сервер: перевірка ролей → антифрод (3 шари) → угода в БД
   ▼
Продавець отримує від сервера EIP-712 підпис і вносить USDT в ескроу
   │  createDeal(підпис) → approve → deposit           (30 хв на оплату)
   ▼
Покупець платить гривнею з власної картки і тисне «Я оплатив»
   │  ім'я відправника → markPaid → повторна оцінка антифродом
   ▼
Продавець бачить кошти в банку (не скріншот!) і підтверджує
   │  сервер: антифрод → approveRelease  (середній ризик — підпис гаманцем / модератор;
   │                                       високий — freezeDeal до рішення адміна)
   ▼
confirmRelease → контракт відправляє USDT покупцю
```

* **Без оплати 30 хв** кіпер викликає `cancel`, і USDT повертаються продавцю.
* **Спір**: сторона натискає «Відкрити спір» (`openDispute`). Модератор дає рекомендацію, адміністратор виконує `resolveDispute` зі свого гаманця. Сервер звіряє розподіл коштів із подією `DisputeResolved` у блокчейні.
* **Чат** є всередині кожної угоди. Після закриття угоди повні номери карток у чаті автоматично маскуються.
* **Журнал** фіксує кожну дію в угоді (час, адреса гаманця, дія, tx hash), а також окремо всі дії адмінів і модераторів.

**Стек:** Next.js 15 (App Router) + TypeScript + Tailwind 4 · Reown AppKit + wagmi 2 + viem · Supabase Postgres + RLS · Solidity 0.8.28 + Hardhat + OpenZeppelin 5.

## Швидкий старт

Потрібні **Node.js 20+** (перевірено на 22) і гаманець **Trust Wallet** або **MetaMask**.

```bash
cd loops-trd/contracts && npm install
cd ../web && npm install
cp .env.example .env.local
```

### 1. Reown Project ID

Project ID потрібен, щоб підключати гаманці через WalletConnect (Trust Wallet на телефоні, MetaMask Mobile).

1. Зареєструйтесь на **https://dashboard.reown.com**.
2. **Create Project** → тип **AppKit** → фреймворк **Next.js**.
3. Скопіюйте **Project ID** у `NEXT_PUBLIC_REOWN_PROJECT_ID`.
4. У налаштуваннях проєкту (**Domain / Allowlist**) додайте свої домени: `localhost:3000` і продакшн-домен.

Без Project ID сторінка входу покаже попередження, а WalletConnect не працюватиме.

### 2. Supabase

1. Створіть проєкт на **https://supabase.com** (регіон — найближчий, наприклад Frankfurt).
2. Застосуйте міграції одним із двох способів:
   * **SQL Editor** → по черзі виконайте файли з `web/supabase/migrations/` (спершу `…_init.sql`, потім `…_rls.sql`);
   * або через CLI:
     ```bash
     cd loops-trd/web
     npx supabase login
     npx supabase link --project-ref <ref>
     npx supabase db push
     ```
3. **Project Settings → Database → Connection string → Session pooler** (порт **5432**). Скопіюйте рядок у `DATABASE_URL` і підставте пароль бази.
4. `SESSION_SECRET` — випадковий рядок довжиною ≥ 32 символи (`openssl rand -base64 48`). Можна взяти **Legacy JWT secret** із *Project Settings → API → JWT Settings*: тоді сесійний токен Loops Trd буде дійсним JWT і для Supabase API (`sub` = id профілю, `role` = `authenticated`).

**Як працює авторизація.** Вхід — SIWE (підпис гаманцем), а не Supabase Auth. Сервер перевіряє підпис і видає httpOnly-cookie з JWT. Кожен запит від імені користувача виконується в транзакції з `SET LOCAL ROLE authenticated` і `request.jwt.claims`, тобто так само, як це робить Supabase PostgREST. Тому всі **RLS-політики діють навіть для серверного коду**. Привілейовані зміни (статуси угод, рішення адміна) сервер робить лише після явної перевірки прав.

### 3. Тестові BNB з фаусета

Газ у BSC Testnet оплачується тестовими BNB (tBNB). Вони потрібні:

* **деплоєру** контракту;
* **серверному гаманцю антифроду** (`BACKEND_SIGNER_PRIVATE_KEY`): він надсилає `approveRelease`, `freezeDeal`, `cancel`;
* **кожному учаснику** (депозит, «Я оплатив», підтвердження) та **адміну** (`resolveDispute`).

Як отримати:

1. Додайте мережу в гаманець: **BNB Smart Chain Testnet**, chainId **97**, RPC `https://data-seed-prebsc-1-s1.bnbchain.org:8545`, символ **tBNB**, експлорер `https://testnet.bscscan.com`. AppKit запропонує додати мережу автоматично.
2. Відкрийте офіційний фаусет **https://www.bnbchain.org/en/testnet-faucet**, вставте адресу й отримайте tBNB. Фаусет може вимагати невеликий баланс BNB у mainnet або вхід через GitHub. Альтернативи — фаусети QuickNode, Chainstack тощо.
3. Тестові **mUSDT** учасник отримує прямо в кабінеті кнопкою «Отримати 1000 mUSDT» (функція `faucet()`, раз на годину).

> Створіть **окремі** тестові гаманці для деплоєра та сервера. Ніколи не використовуйте ключі від гаманців з реальними коштами.

### 4. Деплой контракту

```bash
cd loops-trd/contracts
cp .env.example .env
#   DEPLOYER_PRIVATE_KEY=0x…        тестовий ключ із tBNB
#   ADMIN_ADDRESS=0x…               гаманець адміністратора (DEFAULT_ADMIN_ROLE + ARBITER_ROLE)
#   BACKEND_SIGNER_ADDRESS=0x…      адреса з BACKEND_SIGNER_PRIVATE_KEY (SIGNER_ROLE + FREEZER_ROLE)
npm test                    # 65 тестів
npm run deploy:testnet      # MockUSDT + LoopsTrdEscrow → deployments/bscTestnet.json
```

Скрипт видає ролі серверному гаманцю й передає права адміна на `ADMIN_ADDRESS`, після чого деплоєр відмовляється від своїх ролей. Адреси з `deployments/bscTestnet.json` впишіть у `web/.env.local` як `ESCROW_ADDRESS` і `USDT_ADDRESS`.

Якщо `npx hardhat compile` не може завантажити компілятор (фаєрвол), запускайте з `USE_SOLCJS=true`. Тоді використовується solc-js із npm.

Після зміни контракту оновіть ABI у вебзастосунку: `npm run export-abi`.

### 5. Запуск сайту

```bash
cd loops-trd/web
npm run dev          # http://localhost:3000
# продакшн:
npm run build && npm start
```

Перевірте, що `APP_DOMAIN` **точно** збігається з адресою в браузері (`localhost:3000` або `loops.example.com`), бо інакше SIWE-вхід буде відхилено.

**Деплой на Vercel:** імпортуйте репозиторій, вкажіть **Root Directory** `loops-trd/web`, додайте всі змінні з `.env.example`. Cron із `vercel.json` викликатиме кіпер. Vercel сам передає `Authorization: Bearer $CRON_SECRET`.

### 6. Перший адміністратор та інвайти

1. Впишіть адресу свого гаманця в `BOOTSTRAP_ADMIN_WALLET`. Це має бути той самий гаманець, що й `ADMIN_ADDRESS` у контракті, щоб ви могли виконувати `resolveDispute`.
2. Увійдіть цим гаманцем: профіль адміна створиться автоматично. Це спрацьовує лише один раз, поки в системі немає жодного адміністратора.
3. **Адмінка → Учасники → Інвайт-коди**: згенеруйте одноразовий код із терміном дії від 1 до 30 днів і надішліть другу. Код показується один раз, у БД зберігається лише його хеш.
4. Друг входить з кодом, заповнює профіль (ім'я, Telegram, ім'я власника картки, останні 4 цифри). Статус стає «Очікує підтвердження».
5. Ви схвалюєте заявку. Критичні дії адміна підтверджуються **підписом гаманця**: сервер фіксує дію та її дані в одноразовому nonce і перевіряє підпис саме вашого гаманця.

### 7. Автоскасування (кіпер)

`GET /api/cron/keeper` із заголовком `Authorization: Bearer $CRON_SECRET`:

* скасовує в БД угоди, де продавець не вніс USDT за 30 хв;
* викликає `cancel` у контракті для угод без оплати після дедлайну (кошти повертаються продавцю), окрім угод зі спором;
* синхронізує стан активних угод із блокчейном.

Запускайте його кожні 1–5 хв: Vercel Cron (на тарифі Hobby — лише раз на день), cron-job.org, GitHub Actions або системний cron.

## Ролі та права

Права перевіряються **на трьох рівнях**: інтерфейс → сервер (`src/server/services`) → RLS у Postgres. Ще один рівень — сам смарт-контракт.

| Дія | Учасник | Модератор | Адмін |
|---|:-:|:-:|:-:|
| Свої оголошення та угоди, чат угоди | ✓ | — | — |
| Бачити чужі угоди, чат, сигнали ризику | — | ✓ | ✓ |
| Рекомендація у спорі | — | ✓ | ✓ |
| Підтвердити перевірку середнього ризику (кошти все одно відпускає лише продавець) | — | ✓ | ✓ |
| Відпустити кошти покупцю | лише продавець своєї угоди | **ніколи** | **ніколи** |
| `resolveDispute`, `unfreezeDeal` (контракт) | — | — | ✓ (ARBITER_ROLE) |
| Схвалення/блокування учасників, ролі, ліміти, інвайти | — | — | ✓ + підпис гаманцем |
| Налаштування антифроду, чорний список | — | перегляд | ✓ + підпис гаманцем |
| Журнал дій персоналу | — | свої дії | усі |

## Антифрод

Окремий серверний модуль `web/src/server/antifraud/`. `engine.ts` — чиста функція, `repository.ts` збирає факти з БД.

**Шар 1 — жорсткі правила** (миттєве блокування до депозиту або заморожування після нього):
гаманець, картка (4 цифри), пристрій чи IP у чорному списку · перевищення разового або добового ліміту · ризиковий гаманець за AML-перевіркою (`AmlProvider`; зараз заглушка, є каркас `AmlBotProvider` для підключення AMLBot).

**Шар 2 — сигнали з вагою й поясненням:** новий/невідомий/спільний пристрій (FingerprintJS open-source), спільний IP, ознаки VPN/проксі (`IpIntelProvider`, зараз евристика за заголовками), нетиповий часовий пояс · граф зв'язків (спільні картки, гаманці, пристрої, IP; пов'язані між собою покупець і продавець) · швидкість (угоди за 1 год, обсяг за 24 год проти середнього за 30 днів) · поведінка (різкий ріст суми, нетиповий час, надто швидка оплата чи підтвердження) · репутація (вік акаунта, успішні угоди, програні спори) · невідповідність імені відправника.

**Шар 3 — комбінації**, наприклад «новий акаунт + новий пристрій + велика сума → високий ризик».

**Рішення:** низький ризик — автоматично; середній — підпис продавця гаманцем або перевірка модератором (налаштовується); високий — угода заморожується, ескроу не відпускає кошти до рішення адміна. Кожна оцінка зберігається в `risk_assessments` разом зі спрацьованими сигналами й поясненнями українською.

**Ліміти** (разовий і добовий) зростають з кількістю успішних угод. Рівні редагуються, адмін може задати персональні ліміти.

**Зворотний зв'язок:** адмін позначає вирішені спори як «шахрайство» або «чесна угода». На вкладці «Точність сигналів» видно precision/recall кожного сигналу. Ваги, параметри, пороги й комбінації редагуються в адмінці без зміни коду і зберігаються в `antifraud_settings`.

**Чому клієнт не може обійти антифрод:** `createDeal` у контракті вимагає EIP-712 підпис серверного ключа (`SIGNER_ROLE`), прив'язаний до id угоди, сторін, суми та терміну дії. Підпис видається лише після оцінки антифродом. Усі угоди створюються з `reviewRequired = true`, тож `confirmRelease` спрацює тільки після серверного `approveRelease`. Прямі записи в таблиці угод для клієнтів заборонені на рівні прав БД.

## Безпека та обмеження

* Ми **не зберігаємо** документи, фото, повні номери карток, приватні ключі чи seed-фрази. Повний номер картки продавець надсилає в чаті угоди, і після закриття угоди він автоматично маскується.
* Відбиток браузера та часовий пояс надсилає клієнт, тому їх можна підробити. Це лише сигнали ризику, а не доказ.
* Визначення VPN/проксі зараз евристичне. Для точності підключіть сервіс IP-розвідки через `IpIntelProvider`.
* AML-перевірка — заглушка (`AML_STUB_HIGH_RISK` для тестів). Для AMLBot реалізуйте запит у `AmlBotProvider` за їхньою офіційною документацією.
* Серверний ключ (`BACKEND_SIGNER_PRIVATE_KEY`) може лише підписувати створення угод, заморожувати їх і дозволяти відпуск. Перевести кошти собі він не може. Тримайте його в секретах хостингу.
* Модератор не має жодної ролі в контракті.
